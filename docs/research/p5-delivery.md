# P5 README 与 PR · 开源调研

调研日期：2026-10-23。目标：交付一份「看得懂边界」的 README 与一个字段齐全的 PR。

## 候选

| # | 候选 | 许可 | 与本阶段的关系 |
|---|---|---|---|
| 1 | Keep a Changelog 1.1.0 | CC BY 4.0 | 变更分类口径（Added / Changed / Removed / Fixed） |
| 2 | Conventional Commits 1.0.0 | CC BY 3.0 | 提交前缀与 breaking change 标注 |
| 3 | GitHub PR 模板（社区通用五段式） | 无固定许可 | 描述结构参考 |

## 可借鉴做法（落到文件/组件级）

1. **变更按「新增 / 修改 / 删除 / 修复」四类分条，而不是流水账。**
   落到 `README.md` 的「本次改动清单」与 `docs/delivery/change-list.md`。四类口径能直接回答「删掉了什么」，这对本项目尤其重要——`mockData.ts` 与 `tel:` 链接是被**删除**的，藏在「修改」里会误导评审。

2. **提交信息用中文分条，标题保留 `feat/fix/docs/test` 前缀。**
   落到本次提交。前缀便于 `git log --oneline` 扫读，正文分条便于逐条对照改动清单。

3. **PR 描述固定五段：谁做的 / 改了什么 / 怎么验的 / 没做什么 / 风险点。**
   落到 PR 正文。「没做什么」是本项目最容易含糊的一段：没有后端、没有真实通知、没有部署，必须显式写出，避免把演示读成已上线。

## 不采纳及原因

- **Conventional Commits 的英文正文与 scope 规则**：本项目提交历史与文档均为中文，强制英文正文会降低可读性；只借用前缀，不借用语言。
- **自动生成 changelog 工具（conventional-changelog 等）**：需要额外依赖与 git 钩子，收益不足以覆盖成本。

## 结论

README 用「演示 vs 生产」双栏对照表承载边界，避免读者把合成原型当成可运营系统；PR 用五段式，缺一段都不算完整。
