# 双向缺口报告

更新：2026-10-23。目的：把「哪一端有、哪一端没有」和「需求有、代码没有」写清楚，避免读者把演示能力当成已实现能力。

## 一、B 端有能力、A+ 端不消费

| B 端能力 | A+ 现状 | 原因 / 影响 |
|---|---|---|
| 求助订单全流程（接单 / 签到 / 完成 / 取消 / 争议） | 不参与 | A+ 是受理登记台，不做上门履约。社区桥只把「审核通过的求助帖」映射成受理记录，并**只读展示**社区订单状态标签 |
| 志愿动态、邻里帖、闲置互助 | 不读取 | 桥只映射 `mode === 'help'` 的帖子；其余类型与 A+ 受理无关 |
| 点赞 / 收藏 / 评论 / 举报 | 无 | A+ 无社区互动面 |
| 时间币账本（`unsettled` 只读流水） | 不展示 | A+ 无账本视图；账本只在 B 的「我的」与订单详情出现 |
| B 的「投诉 / 反馈工单」（`Complaint`） | 不互通 | **两边是不同概念**：B 的是本机反馈工单；A+ 的是「针对演示角色的复核队列」。同名不同义，未做映射，避免把两类记录混成一个队列 |
| 身份体系 `visitor / member / reviewer` | 不映射 | A+ 用 `demo-intake / demo-review / demo-referral` 三个演示角色，与 B 的成员身份没有对应关系；两侧都明确写「不是真实账号或权限」 |

## 二、A+ 端有能力、B 端不展示

| A+ 能力 | B 端现状 | 说明 |

## 四、两端共有的边界

- **无后端**：没有 API、数据库、鉴权、会话；所有状态在当前浏览器。
- **无真实通知**：不投递短信/推送/邮件/IM。
- **无上传/定位/支付**：没有文件、坐标、金额。
- **无部署**：未绑定域名、未开 GitHub Pages、未接 CDN。
- **仅合成数据**：所有姓名、社区、订单、留言、时间线均为虚构。

## 五、已知技术债与风险（按影响排序）

1. **B 端坏档恢复路径弱于 A+**（真实缺口）：A+ 有「发现无法读取的旧存档 → 必须下载原文 → 才能重置」，B 只有重置。建议下一步把 A+ 的 `unreadableStoredData` 流程搬到 B。
2. **A+ 全树重渲染**：`revision` 计数器让任意 store 变化触发整棵 A+ 树重算。当前节点量（数百）无感；记录上千或时间线上万时需改为按字段订阅。
3. **`computed` 不缓存**：派生在每次读取时重算（`filteredCases`、`communityRegisteredCases` 等）。规模小时可接受，是换取「不会失效」的取舍。
4. **`AppContext.tsx` 仍是 623 行单点**：契约被钉死（字段名与签名不变）所以未拆分；后续拆分要先补契约测试。
5. **验收只在 Chromium**：未覆盖 Firefox/Safari/微信 X5。
6. **截图不入库**：`docs/evidence/**/*.png` 被 `.gitignore` 排除，评审需本地跑脚本复现。
7. **A+ 未移植 `OfflineNotice`**：mvp 有离线提示组件；232 无 Service Worker，本轮不引入 PWA，因此省略。若后续加离线，需要连同预缓存一起做。
8. **备份导入（文件选择）未自动化**：导出与刷新持久化已覆盖；`input[type=file]` 的赋值在 CDP 下需要 `DOM.setFileInputFiles`，本轮未接。

## 六、结论

当前交付是一个**边界清楚的合成演练原型**：核心流程（发布 → 先审后发 → 接单/受理 → 双方确认 → 只读记账）可完整走通，合规红线以「拦截 + 提示 + 留痕 + 明确声明」的方式落地，**但没有任何生产能力**。任何「已实现」的表述都应理解为「在本机合成数据上可演示」。
